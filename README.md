# library_gui — локальное GUI для библиотеки FB2/EPUB

Одно настольное приложение на Rust (egui/eframe). **Никаких HTTP-серверов**:
UI, пайплайн и поиск живут в одном процессе, общаются через каналы.

Рассчитано на библиотеку 500 000+ книг: метаданные читаются в память один раз,
поиск идёт через Tantivy, книги лежат упакованными в `.arx` и извлекаются
по одной только тогда, когда книгу открывают.

---

## Как это устроено

```
        UI-поток (egui)                   фоновый поток (worker)
   ┌──────────────────────┐          ┌─────────────────────────────────┐
   │ поиск, список, детали│          │ ZIP → FB2 → EPUB 3.3 → WebP/AVIF│
   │ прогресс-бар         │◀─────────│ → ARX → Tantivy                 │
   └──────────────────────┘  канал   └─────────────────────────────────┘
              │ crossbeam-channel
              ▼
        db::Library — поиск и `arx dump`
```

| Файл | Что делает |
|---|---|
| `src/main.rs` | `App` (всё состояние), канал, `eframe`, служебные режимы `--import`/`--search` |
| `src/ui.rs` | три зоны + прогресс-бар: поиск, список, детали книги |
| `src/worker.rs` | фоновый импорт ZIP, распаковка, батчи по 1000 книг |
| `src/fb2epub.rs` | **свой конвертер FB2 → EPUB 3.3** (без Calibre) |
| `src/db.rs` | `BookMetadata`, индекс Tantivy, поиск с фильтрами, извлечение из ARX |
| `src/genres.rs` | коды жанров FB2 → русские названия (фильтр в интерфейсе) |
| `src/images.rs` | свой оптимизатор картинок: WebP/AVIF, near-lossless, градации серого |

### Каталог данных

```
data/
├── archives/       <от>-<до>.arx           — весь входной ZIP одним томом
├── covers/         <id%1000>/<id>.<формат> — обложка книги (копия из EPUB)
├── metadata/       <id%1000>.jsonl         — метаданные, по строке JSON на книгу
├── cache/          <id>.epub               — распакованное для чтения (чистится)
├── index/                                  — индекс Tantivy (только для поиска)
└── tmp/                                    — временная папка, чистится после импорта
```

И `covers/`, и `metadata/` разложены по 1000 подкаталогов/файлов через
`id % 1000`. Причина одна: миллион книг. Миллион файлов в одном каталоге —
это миллион записей в одном `readdir`, каталог не влезает в кэш, `ls`, бэкап и
копирование деградируют; а один файл метаданных на несколько гигабайт — это
ещё и одна точка отказа, где повреждение носителя уносит весь каталог, а не
одну тысячную.

Что это даёт:

| | один каталог / один файл | разложено по 1000 |
|---|---|---|
| обложки | 1 000 000 файлов в `covers/` | по ~1000 файлов в каждом из 1000 каталогов |
| метаданные | ~4 ГБ в `metadata.jsonl` | по ~4 МБ в каждом из 1000 файлов |
| цена повреждения | весь каталог | одна тысячная |

`metadata/*.jsonl` пишется дописыванием в конец с `flush` и `fsync` после
каждого файла: если импорт убьют посреди работы, потеряется максимум одна
незавершённая строка. Формат построчный, поэтому битая строка стоит **одной
книги**, а не файла — остальные читаются, а в консоль выводится, сколько строк
пропущено. Старый единый `data/metadata.jsonl` по-прежнему читается, так что
библиотека, собранная прежней версией, открывается без миграции.

Обложки старых библиотек, лежащие плоско (`covers/<id>.avif`), тоже
продолжают работать: путь в `cover` — это просто относительный путь внутри
`covers/`.

Путь к каталогу — первый аргумент (`library_gui /path/to/data`, по умолчанию `data`).

## Пайплайн импорта

Порядок ровно такой, и **ни один шаг не пропускается молча**:

1. **Распаковка** ZIP во временную папку (только `.fb2`, basename — защита от `../`).
2. **На каждую книгу** (параллельно, по числу ядер):
   1. **метаданные** — `<book-title>`, `<author>` и `<genre>` из FB2
      (коды жанров переводятся в названия при загрузке, см. ниже);
   2. **конвертация** — своя, `fb2epub::convert(<книга.fb2>, <книга.epub>)`:
      разбор `quick-xml`, сборка EPUB 3.3 крейтом `zip`, ни одного дочернего
      процесса (см. ниже);
   3. **оптимизация картинок** — свой оптимизатор: **WebP или AVIF**, уменьшение
      до 480×720 плюс дополнительные −55 % по длинной стороне; quality 40
      (у картинок меньше 300 px — 48), WebP `sns_strength=80`, `filter_strength=70`,
      near-lossless для png/gif/bmp, градации серого — одним каналом; из
      вариантов берётся **наименьший** по байтам;
   4. **проверка** — если хоть одна картинка осталась не-WebP и не-AVIF, книга
      считается сбойной (не «тихо пропускаем»);
   5. **минификация текста** — XHTML/CSS: комментарии и лишние пробелы;
      из OPF вычищаются метаданные Calibre (`src/images.rs`, `minify_xhtml`,
      `minify_css`, `strip_calibre_metadata`);
   6. **subsetting шрифтов** — встроенные `.ttf`/`.otf` ужимаются до символов,
      которые реально есть в тексте книги (`hb-subset`, см. ниже);
   7. **чистка контейнера** — `toc.ncx` (в EPUB 3 его заменяет `nav.xhtml`)
      удаляется вместе со своим `<item>` в OPF и атрибутом `spine toc="…"`;
   8. **обложка** — берётся готовый кадр из EPUB и кладётся в
      `data/covers/<id>.<формат>`. Второй раз её никто не кодирует: раньше
      обложка проходила энкодер дважды, и это стоило ~12 % всего времени импорта;
   9. в stderr пишутся битые ссылки на картинки (дефект исходного FB2, не сбой).
3. **Упаковка** — всё, что дал один входной ZIP, кладётся в **один** архив:
   `arx create -f -c zstd=19 --dir-as-root -o data/archives/<min>-<max>.arx <папка>`.
   Батчей нет: ZIP уже пришёл нарезанным, дробить его ещё раз незачем. Имя
   архива — диапазон ID книг внутри (`821884-823922.arx`).
   Записи внутри EPUB при этом **не сжимаются** (`ImageOptConfig::epub_stored`):
   так zstd жмёт архив целиком и экономит ещё ~21 % — подробности в разделе
   «Бенчмарк: сколько даёт каждый шаг».
4. **Индекс** — книги добавляются в Tantivy (бюджет памяти 50 МБ) и в `metadata.jsonl`.
5. **Уборка** — временные папки удаляются.

### Свой конвертер FB2 → EPUB 3.3

Calibre из пайплайна убран совсем: `ebook-convert` больше не вызывается, и в
системе он не нужен. Конвертация — `src/fb2epub.rs`, зависимости только
библиотечные: `quick-xml` (разбор) и `zip` (запись, тот же крейт, что и в
оптимизаторе).

**Почему не крейт `fb2`.** Он был первой попыткой: разбирает FB2 через serde в
готовые структуры. Но у него жёсткий перечень жанров FB2, и на реальном архиве
**5 книг из 14 не разобрались** — `unknown variant 'boyar_anime'`, `popadancy`,
`network_literature`. Это ровно те современные коды lib.rus.ec, которые уже
есть в `src/genres.rs`. Своя обёртка над `quick-xml` таких списков не знает и
разбирает все 14.

**Почему не `epub_builder`/`lib-epub`.** Нужны ровно EPUB 3.3, `nav.xhtml` и
`<aside epub:type="footnote">`; проще записать пять видов файлов самому, чем
подстраивать чужой генератор (он же пишет `toc.ncx`, от которого мы уходим).

Что делает конвертер:

| Требование | Как выполнено |
|---|---|
| Версия | `version="3.3"` в `content.opf`, обязательный `dcterms:modified` |
| Оглавление | `nav.xhtml` с `<nav epub:type="toc">`, `toc.ncx` не создаётся вообще |
| Сноски | `<body name="notes">` → `<aside epub:type="footnote" id="fn-…">`, ссылки → `<a epub:type="noteref">`, обратно — `<a epub:type="backlink">` |
| Сноски в TOC | примечания лежат в `notes.xhtml` и в `nav` не попадают; для них есть только `epub:type="endnotes"` в `landmarks` |
| Стиль | один `css/unified.css`; у заголовков нет ни рамок, ни фона, ни обводок |
| Картинки | все `<binary>` (base64) распаковываются в `images/`, имя обложки — `cover.<ext>` |
| Мусор | ни старых калибровских стилей, ни шрифтов, ни `page_styles.css`, ни `titlepage.xhtml` |

Разбор FB2 идёт своим деревом (`Element`/`Node`), а не по фиксированной схеме:
незнакомый тег не роняет книгу, а прозрачно пропускается. Сущности
(`&amp;` и т.п.) приходят отдельным событием `GeneralRef` и собираются обратно,
поэтому текст не теряется. Если FB2 ссылается на примечание или иллюстрацию,
которой в файле нет, — в текст ставится заметная заглушка, а дефект попадает в
отчёт импорта (громко, а не молча).

**Про `epublift`.** В ТЗ упомянут `epublift optimize … --webp …`. В реальном
`epublift` 4.4.1 **нет подкоманды `optimize`** и нет флагов
`--webp-quality/--max-w/--max-h/--webp-method` (реальная форма —
`epublift -i IN -o OUT -r REPORT --webp -q 35`), а флаг `--webp` не гарантирует,
что *все* картинки станут WebP. Поэтому оптимизация сделана своим кодом в
`src/images.rs` — он даёт ровно 100 % WebP/AVIF и полный контроль над размером.

## Чем именно уменьшается размер

| Слой | Технология | Эффект |
|---|---|---|
| WebP | `libwebp` (FFI, `libwebp-sys`) | lossy q35/q50 + near-lossless (`lossless=1`, `near_lossless=60`) |
| AVIF | `image` 0.25 → `ravif` (чистый Rust) | lossy q35/q50; обложки — только AVIF q50 |
| Градации серого | свой детектор пикселей | один канал (`L8`) вместо трёх |
| Уменьшение | `image` 0.25, Lanczos3 | до 600×900 + ещё −45 % по длинной стороне |
| Выбор варианта | свой перебор кандидатов | берётся **наименьший** результат каждой картинки |
| Минификация | свой XML-безопасный минификатор | XHTML/CSS/OPF: комментарии и пробелы; `<pre>` не трогается |
| Шрифты | `hb-subset` (HarfBuzz) | встроенный шрифт ужимается до символов книги |
| Чистка контейнера | свой разбор OPF | `toc.ncx` + его `<item>` + `spine toc="…"` |
| Упаковка EPUB | `zip` 6, `mimetype` первым и Stored | OCF-совместимость; остальное — Stored (см. ниже) |
| Упаковка ARX | `arx` 0.4.2, `-c zstd=19` | жмёт батч целиком, потому что внутри EPUB всё лежит без сжатия |
| Поиск | Tantivy, память ≤ 50 МБ | быстрый поиск без загрузки книг |

Почему `zstd`, а не `lzma=9`: на уже сжатых (Deflate) EPUB сумма книг и `.arx`
с LZMA совпадали (9.92 МиБ против 9.93 МиБ) — сжимать нечего. Но если записи
EPUB не сжимать, `zstd=19` обгоняет `lzma=9` и работает в разы быстрее:
5 804 500 Б против 5 819 489 Б на тех же 14 книгах.

## Сборка и запуск

```bash
cd library_gui
sudo pacman -S nasm        # ассемблер для rav1e, см. ниже
cargo build --release

./target/release/library_gui                  # окно, данные в ./data
./target/release/library_gui /путь/к/data     # окно с другим каталогом данных
```

**Про `nasm`.** По умолчанию включена фича `asm` — ассемблерные ядра rav1e,
который кодирует AVIF. Это тот же самый кодировщик с теми же настройками:
файлы получаются такие же, но импорт идёт **в 1.77 раза быстрее** (140 с
против 247 с на 100 книгах). Стоит только времени сборки, по размеру архива —
ровно ноль.

Если `nasm` поставить нельзя, соберите без него — будет работать, но медленнее:

```bash
cargo build --release --no-default-features --features fonts
```

Служебные режимы без окна (удобно для проверки и пакетных импортов):

```bash
./target/release/library_gui --import <архив.zip> [data_dir]
./target/release/library_gui --search "<запрос>"  [data_dir] [--author X] [--genre Y]
./target/release/library_gui --convert <fb2> <epub>   # конвертер отдельно
./target/release/library_gui --image <файл>… [--out кат]  # сжать картинки
./target/release/library_gui --bench <zip> [каталог]  # замер каждого шага
./target/release/library_gui --help
```

**Отдельная картинка.** `--image` сжимает файл **ровно тем же кодом**, что и
импорт (уменьшение по лестнице, выбор AVIF/WebP, скорость rav1e), поэтому
результат совпадает с тем, что попадёт внутрь книги:

```bash
./target/release/library_gui --image photo.jpg           # рядом photo.avif
./target/release/library_gui --image *.jpg --out out/    # все в out/
```

Настройки те же, что у импорта, и читаются из тех же переменных
(`LIBRARY_QUALITY`, `LIBRARY_MAX_W`, `LIBRARY_SHRINK`, `LIBRARY_AVIF_SPEED`…).
Пример на реальном файле 1290×1448, 862 КБ:

```
photo.jpg → photo.avif
  image/avif, 1290×1448 → 480×539 (уменьшено), 862410 Б → 15527 Б (-98.2 %)
```

Внешних программ для импорта не нужно: конвертация FB2 → EPUB своя, картинки
пережимаются через `libwebp` (линкуется в бинарник), шрифты — через HarfBuzz
(тоже линкуется). Из утилит остаётся только `arx` — им книги упаковываются и
распаковываются.

Зависимости для окна (проверены в системе): GTK3, `xkbcommon`, `wayland-client`,
`x11`. Читалка: `foliate`, с откатом на `xdg-open`.

Subsetting шрифтов — единственная зависимость, которой нужны заголовки и
`clang` на этапе сборки (`hb-subset` → `bindgen`). Если их нет:

```bash
sudo pacman -S harfbuzz clang     # или apt install libharfbuzz-dev clang
cargo build --release --no-default-features   # собрать совсем без шрифтов
```

### Ярлык в меню приложений

```bash
./install.sh            # иконка + ярлык, найти поиском: «Библиотека» или «FB2»
./install.sh --remove   # убрать
```

Скрипт рендерит `assets/icon.svg` в 8 размеров (`rsvg-convert`), кладёт их в
`~/.local/share/icons/hicolor/<размер>/apps/library_gui.png` и создаёт
`~/.local/share/applications/library_gui.desktop` с `Exec` на этот каталог
данных. Иконка также встроена в бинарник (`assets/icon-256.png`), поэтому
окно и панель задач выглядят одинаково даже без установленного ярлыка.

### Интерфейс

* **Сверху, в три строки** — заголовок и счётчик книг; поиск (ищет на
  лету), «📥 Импортировать ZIP…» (`rfd`), число потоков (0 = все ядра) и
  кнопка кэша; ниже — фильтры по автору и жанру со счётчиком найденного.
  Фильтры специально сверху, а не сбоку: место по бокам нужно обложкам.
* **В центре** — сетка обложек: обложка вместо названия, а у книг без
  обложки на её месте нарисован прямоугольник с названием. Сетка
  перестраивается под ширину окна, поэтому в развёрнутом окне колонок
  больше. Наведение показывает название и автора.
* **Справа панели нет.** По клику на обложку открывается отдельное окно
  «📖 Книга»: название, автор, кнопка «📖 Читать», затем все метаданные —
  авторы, жанры, серия, год, дата, издательство, город, ISBN, язык и язык
  оригинала, переводчики, ключевые слова, размер, архив, путь внутри
  архива, ID, ID FB2, версия, дата документа, программа, источник, OCR, —
  и сворачиваемые аннотация и оглавление. Окно закрывается крестиком, а
  сетка остаётся на месте.
* **Снизу** — прогресс-бар, текущая книга, число потоков, число
  пропущенных и битые ссылки.

Кнопка «Читать» стоит сразу под названием, а не в конце длинной
прокрутки: иначе до неё пришлось бы долистать. Кнопки «Извлечь в папку»
нет — сохранение в произвольную папку убрали, книга просто попадает в
кэш и открывается читалкой.

UI никогда не блокируется: импорт идёт в отдельном потоке, канал читается
в начале каждого кадра. Сетка рисует только видимые строки
(`ScrollArea::show_rows`), поэтому и на 500 000 книг в кадр не попадает
лишняя тысяча картинок.

### Фильтры по автору и жанру

Оба фильтра складываются с текстовым поиском и друг с другом.

* Списки авторов и жанров — это **фасеты**: они считаются по книгам,
  подошедшим под текстовый запрос, но **без учёта самих фильтров**. Иначе
  после выбора автора в списке остался бы только он один.
* Пустой запрос означает «вся библиотека»: тогда перебираются все книги
  в памяти, поэтому фильтр по жанру работает по всей библиотеке, а не
  только по первой странице выдачи.
* Списки ограничены 500 пунктами (`FACET_LIMIT`): в библиотеке на 500 000
  книг авторов бывают десятки тысяч, и рисовать их все нельзя. Редкого
  автора проще найти строкой поиска.

### Кэш распакованных книг

Чтение устроено так: `arx dump <архив> <путь>` вытаскивает один `.epub`
(архив целиком не распаковывается), файл кладётся в `data/cache/<id>.epub`
и открывается читалкой (`foliate`, иначе `xdg-open`).

* Кэш лежит **рядом с библиотекой**, а не в системном `/tmp`: оттуда его
  неудобно чистить и он теряется при перезагрузке.
* В верхней панели видно `🧹 кэш: 12 МБ`, а по нажатию он очищается.
* Если кэш перерос `CACHE_LIMIT_BYTES` (2 ГБ), перед чтением самые старые
  файлы удаляются автоматически (`prune_cache`) — на 500 000 книг иначе
  накопились бы сотни гигабайт.
* Логика покрыта тестом `db::tests::cache_usage_prune_and_clear`
  (`cargo test --release`).

### Метаданные книги

Из `<title-info>` и `<document-info>` FB2 берутся все поля, которые там есть:

* `title-info` — название, все авторы, жанры, аннотация, ключевые слова,
  язык, язык оригинала, переводчики, серия и номер в ней, дата написания;
* `publish-info` — издательство, город, год, ISBN;
* `document-info` — id, версия, дата, программа, источник, OCR.

Оглавление (`chapters`) берётся из **готового EPUB** — из `toc.ncx`, а если
его нет, из `nav.xhtml`. Это ровно то, что покажет читалка, поэтому главы
не приходится выдумывать из секций FB2.

Всё это лежит в `metadata.jsonl` в поле `details`; старые записи без него
читаются как пустые (`#[serde(default)]`), так что переимпорт не обязателен.

### Как хранятся жанры

В `metadata.jsonl` лежат **коды** FB2 (`sci_history`, `popadancy`), а не
названия. Названия считаются из кодов при загрузке библиотеки, поэтому
уточнение таблицы перевода не требует переимпорта — а на 500 000 книг
переимпорт занял бы около 53 часов.

## Скорость и размер: где уходило время

### Где уходило время

Пофазный профиль (`LIBRARY_PROFILE=1`) на импорте 100 книг:

```
[профиль] календарное время 148.8 с, потоков 16
  картинки                     481.2 с процессорного   94.6 %
  обложки                       22.5 с процессорного    4.4 %
  конвертация FB2→EPUB           3.4 с                  0.7 %
  средняя загрузка: 3.4 ядер из 16
```

То есть узкое место — одно: кодирование картинок. Оно и разбиралось.

### Что сделано

1. **Пул кодирования по картинкам, а не по книгам.**
   Поток на книгу давал параллелизм, но книги неравномерны на порядки: есть FB2
   на 59 МБ и есть книги с одной картинкой. К концу импорта досчитывали две-три
   книги, а 13 потоков ждали. Теперь есть общий на процесс пул
   (`images::encode_pool`), задания нарезаны по картинкам: большая книга
   занимает все ядра, мелкие не плодят потоки. Пул именно свой, а не `rayon`:
   `ravif`/`rav1e` внутри зовут rayon, и заблокированный воркер «крадёт»
   следующую задачу из того же реестра — вложенность растёт до числа картинок и
   рвёт стек.

2. **Обложка кодировалась дважды.** `optimize_epub` уже делала `cover`, а
   потом `extract_cover` декодировала исходник и снова гоняла энкодер. Теперь
   готовый кадр просто копируется в `data/covers/<id%1000>/<id>.<расширение>`.

3. **Обложка кодировалась отдельно от остальных картинок** — всегда в AVIF и
   со своей скоростью. 85 обложек съедали 46 % всей работы над картинками
   (4 с на книгу при speed 2). Теперь обложка идёт общим путём.

4. **Уменьшение упиралось в пол.** `shrink_percent` молча съедался: пол
   масштаба был жёстко 0.65, поэтому любое значение больше 35 % не давало
   ничего. Теперь пол выводится из настройки.

5. **Включён ассемблер rav1e.** У `image` есть фича `nasm`, которая включает
   ассемблерные ядра rav1e, — по умолчанию она выключена, и мы её не включали.
   Результат тот же бит в бит по настройкам, но **140 с вместо 247 с, то есть в
   1.77 раза быстрее**. Требует `nasm` при сборке (см. «Сборка и запуск»).

6. **Проверен профиль сборки.** `opt-level = 3` с `lto = "thin"` и
   `codegen-units = 1` на импорте не дали ничего (247.5 с против 245.6 с —
   шум), поэтому профиль оставлен обычным: время уходит внутри rav1e, а не в
   нашем коде.

### Формат и настройки: замер, а не догадки

Всё измерено на одном и том же импорте: 92 книги из 157 МБ (8 нерусских
отброшено фильтром), `shrink 55 %`.

| Режим | Время | Архив |
|---|---|---|
| WebP m4 q40, 480×720 | **18 с** | 38.10 МБ |
| AVIF q35, 480×720, speed 4 (с asm) | 106 с | 35.14 МБ |
| AVIF q40, 540×810, speed 4 | 179 с | 36.23 МБ |
| AVIF q40, 540×810, speed 2 | 237 с | 35.76 МБ |
| **AVIF q35, 480×720, speed 2 (по умолчанию)** | **140 с** | **34.61 МБ** |
| AVIF q40, 600×900, speed 2 | 251 с | 36.31 МБ |
| AVIF q40, 600×900, speed 1 | 946 с | 36.16 МБ |

Что из этого следует:

* **Мы используем rav1e** (`ravif` 0.13 → `rav1e` 0.8.1, чистый Rust,
  кодирование внутри процесса через `image::codecs::avif`). Это **не самый
  быстрый** кодировщик из доступных, а самый экономный по размеру. Для
  сравнения, те же 31 картинка при одинаковом качестве (SSIM ≈ 0.945):

  | Кодировщик | Время | Размер |
  |---|---|---|
  | SVT-AV1 (speed 8) | 0.6 с | ~590 КБ (+40 %) |
  | libaom (speed 8) | 1.1 с | 566 КБ (+34 %) |
  | **rav1e (наш, speed 2)** | **65 с** | **423 КБ** |

  То есть за скорость SVT-AV1 пришлось бы заплатить 40 % размера — ровно то,
  чего мы избегаем. Если однажды понадобится именно скорость, порядок такой:
  WebP (13×, +9 %) → rav1e `speed 6` (1.8×, +4.8 %) → SVT-AV1 (~100×, +40 %).
* **AVIF против WebP — это −9.2 % размера за 13× времени.** На терабайте
  архива это ~90 ГБ разницы, поэтому по умолчанию стоит AVIF: импорт делается
  один раз, а архив живёт годами.
* **Скорость rav1e почти не работает как рычаг.** `speed 1` против `speed 2` —
  это −0.4 % размера за 3.8× времени. Поэтому стоит `speed 2`, а не `1`.
* **Работают качество и геометрия.** q40 → q35 и 600×900 → 480×720 дают почти
  всю экономию.
* **Скорость rav1e — это отдельная лестница**, и на ней есть точки лучше,
  чем `speed 4`. Всё то же самое, 92 книги, 157 МБ, сборка с `nasm`:

  | speed | Время | Архив | к размеру | 4.8 ГБ |
  |---|---|---|---|---|
  | **2 (по умолчанию)** | **140 с** | **34.61 МБ** | — | 1 ч 11 мин |
  | 4 | 102 с | 35.15 МБ | +1.6 % | 52 мин |
  | 6 | 80 с | 36.28 МБ | +4.8 % | 40 мин |
  | 8 | 60 с | 36.56 МБ | +5.6 % | 31 мин |

  Лучший размен — `speed 4`: +1.6 % размера за 1.37× скорости. `speed 6` и
  `speed 8` дают уже +5 %, а между собой почти не отличаются по размеру,
  поэтому брать `8` смысла нет — только `6`, если нужна скорость.
* **Ассемблер rav1e — единственное ускорение, которое ничего не стоит по
  размеру:** те же байты, в 1.77 раза меньше времени.
* Хромы-субдискретизации в ravif нет (он всегда кодирует 4:4:4), а цветовое
  пространство по умолчанию уже YCbCr, поэтому других резервов сжатия у AVIF
  в этой библиотеке нет.

Вернуться на WebP (в 13 раз быстрее, на 9 % больше): `LIBRARY_WEBP=1`.

### Фильтр «только русские книги»

Язык определяется **по буквам самого текста**, а не по названию: русская книга
с английским заголовком и английской аннотацией в архиве lib.rus.ec — обычное
дело, и по метаданным её не отличить. Считаются буквы всего FB2, причём блоки
`<binary>` (картинки в base64, то есть сплошная латиница) выбрасываются до
подсчёта — иначе любая книга с иллюстрациями выглядела бы английской.

Правила намеренно грубые и безопасные:

* книга отбрасывается, только если кириллицы меньше половины букв
  (**не отбрасывается**, если букв меньше 200 — судить не о чем);
* кириллическая книга отбрасывается, если больше 3 % кириллических букв —
  `і`, `ї`, `є`, `ґ`, `ў`, `ђ`, `ј`, `љ`, `њ`, `ћ`, `џ` (украинский,
  белорусский, сербский);
* всё сомнительное остаётся: потерять русскую книгу хуже, чем пропустить
  нерусскую.

Зазор на реальном корпусе огромный — ложных срабатываний нет:

| Книга | Букв | Кириллицы |
|---|---|---|
| `822277` (русская) | 38 827 | **99.7 %** |
| `823587` (русская) | 510 602 | **99.9 %** |
| `821937` (латышская) | 27 519 | 0.4 % |
| `821947` (латышская) | 153 872 | 0.1 % |

Отброшенные книги никуда не удаляются из исходного ZIP — они просто не попадают
в архив, а список с цифрами, по которым принято решение, пишется в
`data/skipped_foreign.txt`. Отключить фильтр: `LIBRARY_LANG_FILTER=0`;
оставить всю кириллицу (включая украинскую): `LIBRARY_LANG_KEEP_CYRILLIC=1`.

### Как сжимается картинка: пошагово

1. **Декодирование** — `image::load_from_memory`. Что не декодировалось,
   остаётся как есть, и об этом печатается предупреждение: молча не
   пропускается ничего.
2. **Прозрачность и серость** — обход пикселей. Серые картинки пишутся в AVIF
   одним каналом `L8` вместо трёх, непрозрачные — без альфы.
3. **Размер** (`target_dims`): вписать в 600×900, затем уменьшить ещё на 45 % по
   длинной стороне, но не ниже 200 px — иначе иконки превратятся в кашу.
   Ресайз — Lanczos3.
4. **Кандидаты** — все считаются на уменьшенном кадре:
   * WebP lossy: `method 6`, `sns 80`, `filter 70`, q35 (для картинок мельче
     300 px — q50, на мелких артефакты заметнее);
   * AVIF lossy: `ravif`, speed 8, то же качество;
   * near-lossless WebP (`lossless=1`, `near_lossless=60`) — и на уменьшенном
     кадре, и в исходном размере: штриховая графика после Lanczos3 раздувается,
     и вариант «как было» часто выигрывает.
5. **Выбор** — берётся кандидат с наименьшим числом байт, поэтому в архиве
   встречаются оба формата: AVIF выигрывает не всегда.
6. **Замена** — имя записи сохраняется, меняется расширение и `media-type` в
   `content.opf` (точечная правка `href` и `media-type`, а не перезапись OPF).

Посмотреть глазами, что именно теряется, можно так — тест соберёт страницу с
одним и тем же кадром во всех вариантах, в натуральную величину и с
увеличением 2×:

```

xdg-open /tmp/imgcmp/index.html
```

Что **не** работает и поэтому в коде не оставлено:

* **AVIF во внутренней модели YCbCr** (`ColorSpace::Bt709`) — побайтово те же
  данные. `ravif` 0.13 жёстко зашивает `ChromaSampling::Cs444`, а `ColorModel`
  меняет только преобразование RGB→YUV. Настоящий 4:2:0 потребовал бы звать
  `rav1e` напрямую и самим писать AVIF-контейнер.
* **`pass=10` у libwebp** — на 202 байта хуже, чем `pass=1`.
* **Дедупликация одинаковых картинок**: в корпусе 62 байтовых дубля (2.39 МБ
  исходников), но zstd и так жмёт повторы в пределах своего окна — на архиве это
  дало 1 981 Б. Усложнение не окупается.

### Где золотая середина: текст и фотографии

Текст и фотографию нельзя сжимать одинаково. Разница видна в цифрах:
**медианная толщина штриха в корпусе — 2 пикселя**. При общем уменьшении на
35 % она становится 1.3 px, при 50 % — ровно 1 px, то есть буквы слипаются в
серую кашу. Именно поэтому «просто уменьшить всё вдвое» для книги не годится.

Поэтому пайплайн различает картинки по содержимому. «Графика» (текст, схема,
чертёж) — это почти серое изображение со светлым фоном и множеством тонких
штрихов:

```rust
sat < 30.0 && штрихов_на_1000 > 15.0 && доля_фона > 0.3
```

Прозрачность при этом раскладывается на белый фон — иначе RGB под альфой равен
нулю и такая картинка выглядит чёрным квадратом. На корпусе под правило
попадает **194 картинки из 582 (34 %)**.

Для графики включается правило штриха: уменьшать можно, но не сильнее, чем
позволяет её собственная толщина штриха —

```
масштаб >= text_min_stroke / измеренный_штрих
```

При `text_min_stroke = 1.5` картинка со штрихом 2 px уменьшается не более чем
до 75 % (против общих 50 %), а со штрихом 1 px не уменьшается вовсе.

Замеры на реальном архиве (`--import`, 14 книг):

| Вариант | `.arx` | к текущему |
|---|---:|---:|
| как было (q35, −35 %, speed 8) | 5 797 703 Б | — |
| q30, −50 %, speed 4, **вслепую** | 4 175 336 Б | −28.0 % |
| q30, −50 %, speed 4, только правило штриха | 5 037 667 Б | −13.1 % |
| + качество графики 36 | ~5 100 000 Б | −12 % |
| полная защита (графика q42, −25 %) | 5 355 057 Б | −7.6 % |

Видно цену вопроса: слепое уменьшение вдвое экономит 28 %, но убивает текст;
одно только правило штриха сохраняет читаемость и даёт −13 %; «полная защита»
с надбавкой качества стоит ещё 5 % и уже не окупается.

Первый заход на этом и остановился: `q30`, `−50 %`, качество графики 36 и
`text_min_stroke = 1.5`. Архив получался 5 123 168 Б, но **картинки стали
выглядеть заметно хуже** — порог 1.5 px на медиану штриха слишком мягкий
(половина штрихов тоньше медианы), а q36 на тексте даёт звон вокруг букв.
Поэтому следующий раздел переделывает баланс всерьёз.

Посмотреть глазами: тест `img_compare` собирает страницу с тремя текстовыми
картинками и тремя фотографиями в пяти вариантах, в натуральную величину и с
увеличением 2×:

```
cargo test --release -- --ignored img_compare --nocapture
# → сравнение_текста.html
```

### Только AVIF, адаптивная скорость и лестница уменьшения

Что изменилось после жалобы на качество.

**1. WebP убран с горячего пути.** Раньше для каждой картинки кодировались и
WebP, и AVIF, и побеждал меньший — из-за этого в архиве лежали оба формата
(94 картинки были WebP). Теперь основной формат один — AVIF, а WebP остаётся
**только запасным**, если AVIF не закодировался. Плюс: картинки кодируются
вдвое быстрее, и в EPUB больше нет смеси форматов.

**2. Скорость AVIF выбирается по кадру.** `speed` — это не только время, но и
место на кривой «размер↔качество»:

```rust
fn pick_avif_speed(w: u32, h: u32, graphic: bool, is_cover: bool) -> u8 {
    if is_cover || graphic { return 2; }        // текст и обложки — аккуратно
    match (w as u64) * (h as u64) {
        0..=250_000 => 2,                        // до ~500×500
        250_001..=1_000_000 => 3,                // средние фото
        _ => 4,                                  // крупные: иначе ждать минутами
    }
}
```

**3. Вместо одного уменьшения — лестница.** Масштаб считается как самый
сильный допустимый (вписаться в лимит, уменьшить на `shrink` процентов, но не
ниже границы штриха и `min_side`), а дальше по ступеням:

```
0.65 → 0.75 → 0.85 → 1.0
```

Первая ступень, прошедшая проверку качества, и берётся. Если ни одна не
прошла — остаётся исходный размер.

**4. Проверка качества для графики настоящая.** Порог проверяется не по
исходнику, а по **уже закодированному и снова декодированному** кадру: сжатие
тоже размывает края.

```rust
let ok = !graphic || !shrunk
    || decoded_stroke(&cand.data) >= cfg.text_min_stroke * 0.75;
```

**5. Графика после уменьшения подчёркивается** —
`imageops::unsharpen(&resized, 0.7, 2)`. Это стоит 2–5 % сжимаемости, но
заметно возвращает чёткость краёв букв.

#### Выжил ли текст

Отдельный стенд `img_stroke` измеряет штрих **до** и **после** сжатия:

| Штрих после сжатия | Картинок |
|---|---:|
| ≥ 2.0 px | 172 |
| 1.5…2.0 px (на грани) | 0 |
| < 1.5 px | 23 |

Все 23 «плохих» имели штрих 1 px **ещё в исходнике** и вообще не уменьшались
(масштаб 1.00) — сделать их чётче можно было бы только увеличением, что
бессмысленно. Ни одна картинка не потеряла штрих из-за уменьшения.

### Дубликаты: их уже убирает сам архив

`arx` (точнее, контейнер Jubako под ним) хеширует каждое содержимое **blake3**
и переиспользует адрес, если такой хеш уже встречался:

```rust
// jubako-0.4.1/src/creator/content_pack/mod.rs
struct CachedContentAdder<W> { cache: HashMap<blake3::Hash, ContentAddress>, .. }
```

Это дедупликация по всему архиву, без ограничения на расстояние между копиями.
Замеры (`arx create -c zstd=19 --dir-as-root`):

| Что | Вход | Архив |
|---|---:|---:|
| 14 книг | 14.1 МБ | 5 804 448 Б |
| те же 14 книг, 20 копий | 282 МБ | **5 810 635 Б** (+6 187 Б на 19 копий) |
| 1 случайный файл 1 МБ, 20 копий | 20 МБ | 1 002 163 Б |
| 1 текстовый файл 4.2 МБ, 20 копий | 84 МБ | 806 410 Б |

Поэтому в пайплайне своей дедупликации нет: на всём корпусе она дала бы
**1 981 Б** — ровно то, что `arx` уже сделал сам. Это подтвердилось и напрямую:
в корпусе 62 байтовых дубля картинок (2.39 МБ исходников), и вырезание их из
EPUB уменьшило архив на 1 981 Б.

Важное следствие: **область дедупликации — один архив**, а архив теперь ровно
один на входной ZIP. Значит, дедупликация работает в пределах всего ZIP сразу,
а не в пределах искусственного батча: книги `821884` и `823922` из одного ZIP
делят общие картинки, даже если между ними тысяча других книг.

#### Похожие картинки — не дубликаты

Байтовый дубликат — редкость. Гораздо чаще одна и та же картинка лежит в двух
книгах в разном размере или с разным качеством, и хеш её не поймает. Проверил и
это: перцептивный хеш (dHash по серой копии 9×8) + попарная ошибка MSE по
32×32 (`img_neardup`).

| | Групп | Всего байт | arx уже схлопнул | Осталось бы на перцептивную дедупликацию |
|---|---:|---:|---:|---:|
| MSE < 50 | 59 | 1 387 206 | 301 488 | 534 190 |
| MSE < 10 | 57 | 1 353 727 | 301 488 | 517 358 |
| MSE < 2 | 54 | 1 248 350 | 269 771 | 473 966 |

Две вещи из этой таблицы:

1. **Часть уже схлопывается сама.** Пайплайн нормализует картинки — декодирует,
   приводит к одному размеру и кодирует с одним качеством, — поэтому похожие
   исходники нередко дают **побайтово одинаковый** результат, и дальше его
   бесплатно убирает blake3-дедупликация `arx`. Это ~300 КБ на корпусе.

2. **Оставшиеся ~500 КБ (8.6 % архива) требуют подмены картинки.** Убрать их
   можно только одним способом: выбрать в группе одну «каноническую» кодировку и
   подставить её всем остальным — то есть положить в книгу картинку из другой
   книги. Это два прохода по батчу и риск ошибки.

Насколько риск реален, видно на самой крупной группе: dHash собрал в неё
**110 картинок** с «экономией» 724 674 Б. На деле это почти пустые страницы —
разброс яркости 1.8 из 255, MSE между ними 7111. Схлопнув такую группу, мы
уничтожили бы 110 разных картинок ради мнимой экономии. Поэтому в пайплайне
перцептивной дедупликации нет: рычаг «разрешение и качество» из раздела выше
даёт 1.25–1.63 МБ без единого риска, то есть вдвое больше.

Воспроизводится одной командой — она конвертирует каждую книгу, прогоняет её

Что из этого следует:

* **Главный выигрыш даёт не текст, а отказ от Deflate внутри EPUB.** Записи
  EPUB лежат без сжатия (`epub_stored = true`), и `.arx` жмёт батч целиком
  `zstd=19`: **7 379 532 → 5 804 500 Б (−21.3 %)**. Именно поэтому дефолт
  пайплайна — `arx create -c zstd=19` плюс Stored внутри EPUB. Сам по себе
  `zstd` на уже сжатых (Deflate) EPUB не даёт ничего: `none`, `zstd=19` и
  `zstd=22` возвращают одни и те же байты — сжимать внутри нечего.
* **Шаги 1–3 на этих 14 книгах почти пустые** — и это честный результат, а не
  пропуск: свой конвертер и так не пишет ни `toc.ncx`, ни шрифтов, ни
  метаданных Calibre, а XHTML отдаёт без отступов и комментариев, поэтому
  минификация снимает только переводы строк (9.08 → 9.01 МБ, −0.7 % до
  сжатия и −0.2 % после). На чужих EPUB (Calibre, `epub2`, магазины) те же
  шаги снимают в разы больше — минификатор, subsetting и чистка `toc.ncx`
  там включены и работают, что и проверяют тесты в `src/images.rs`.
* **Уровень zstd.** 19 против 22 — одинаковые байты (arx упирается в
  эвристику), а `lzma=9` на тех же данных даёт 5 819 489 Б, то есть чуть
  больше и в разы дольше. Кривая по уровням на 14.1 МБ несжатых записей:
  `zstd=9` — 6 188 882 Б, `12` — 6 055 833 Б, `15` — 5 962 646 Б,
  `17` — 5 820 689 Б, `19` — 5 809 704 Б.
* **Почему импорт не на rayon.** AVIF-энкодер (`image` → `ravif` → `rav1e`)
  сам внутри вызывает `rayon::join`, а `rav1e` уводит работу в свой пул через
  `Registry::in_worker_cross`. Пока поток ждёт, rayon разрешает ему «украсть»
  следующую задачу из своего же реестра — то есть следующую картинку из нашего
  `par_iter`. Каждый уровень добавляет полный кадр энкодера, и вложенность
  растёт вплоть до числа картинок в книге: на дефолтных 2 МиБ это
  гарантированный `has overflowed its stack` (ловилось на 821886, где 226
  картинок). Поэтому книги обрабатываются обычными `std::thread`
  (`spawn_scoped`, стек 16 МиБ), картинки внутри книги — последовательно, а
  глобальному пулу rayon, который достаётся `ravif`, стек выставлен в
  `main`. Воровать становится нечего, и результат при этом не меняется:
  все 582 картинки после переезда побайтово те же.
* **Про `--long=27`.** В `arx` 0.4.2 такого флага нет (`--list-compressions`
  показывает только `None`, `lzma (0->9)`, `zstd (-22->22)`), поэтому
  запрошенный «`zstd 22 --long=27`» выразить нечем. Проверено вручную на том
  же наборе: `tar | zstd -19` — 5 685 805 Б, `tar | zstd -19 --long=27` —
  5 683 519 Б, `tar | zstd -22 --long=27` — 5 681 463 Б. То есть длинное
  окно даёт **0.04 %**, а вся сплошная упаковка вместо `.arx` — 2 %: ради
  этого менять контейнер смысла нет.

### Проверка внешним валидатором

Своей проверки мало: «XML корректный, ссылки разрешаются» не значит «EPUB
валиден». Поэтому результат прогоняется через `epubveri` — независимый

Он нашёл пять настоящих ошибок, которых не видел ни `cargo build`, ни мой
скрипт проверки:

| `RSC-003` | в `container.xml` у `rootfile` стоял `media-type="application/epub+zip"` | правильный OCF-тип `application/oebps-package+xml` |
| `OPF-029`, `PKG-022` | в FB2 `<binary content-type="image/png">` лежал **JPEG**, и мы верили на слово: файл `img0001.png`, MIME `image/png`, а внутри JPEG (24 файла в 821898) | формат определяется по «магическим» байтам (`images::sniff_image`), расширение и MIME берутся из него |
| `OPF-053` | `dc:date` = «2026-09-01 00:43» — свободный текст из FB2, а нужен ISO 8601 | `iso_date()` берёт из строки ведущую дату |

Последний пункт — те самые «битых ссылок в исходниках: 4» (2 в 821897 и 2 в

было. Свой конвертер называет файлы `img0001.png` и пишет ровно столько их,
сколько бинарников в FB2, поэтому такой ошибки не делает.

### Обложки без расширения

Первые три прогона давали 11 обложек из 14, и это списывалось на «свойство
исходников». На самом деле обложки были — просто Calibre кладёт их в EPUB
записью с именем **`cover`, без расширения** (внутри обычный JPEG), а весь
наш код искал картинки по расширению. Отсюда две ошибки сразу:

* обложка не находилась, и книга выглядела как «без обложки»;
* проверка «100 % WebP» её не видела и пропускала JPEG — то есть требование
  «ни одной не-WebP картинки» молча нарушалось ровно у этих трёх книг.
  Прежняя цифра «578 из 578» была неправдой: настоящих картинок 582.

Что сделано:

* картинка определяется ещё и по «магическим» байтам (`looks_like_raster`),
  поэтому `cover` распознаётся и перекодируется в `cover.avif`;
* `count_images` тоже считает по содержимому, а не по имени файла, — теперь
  проверка честная;
* `extract_cover` умеет брать обложку из `<meta name="cover">` в `content.opf`,
  если по имени её не нашёл;
* ссылки на переименованные картинки правятся только внутри `href=`, `src=`,
  `poster=` и `url(...)`. Это важно именно для `cover`: его basename
  встречается ещё в `<meta name="cover" content="id3"/>` и
  `type="cover"`, и простая замена сломала бы OPF;
* `media-type="application/octet-stream"` у этого `item` меняется на
  `image/webp` или `image/avif` — по фактическому расширению.

В `821892.epub` после правки: файл `cover.avif`, в OPF
`<item id="id3" href="cover.avif" media-type="image/avif"/>`,
`<meta name="cover" content="id3"/>` не тронут, в `titlepage.xhtml` —
`xlink:href="cover.avif"`.

Свой конвертер такую запись уже не создаёт — он всегда пишет `cover.<ext>` и
`img<NNNN>.<ext>`, — но вся эта логика осталась: она нужна и для чужих EPUB,
которые могут попасть в библиотеку, и для честного подсчёта картинок.

### Скорость

| Прогон | Время |
|---|---|
| CLI `library_pipeline`, 1 поток | 413 с |
| CLI `library_pipeline`, 16 потоков | 90 с |
| GUI `library_gui`, до распараллеливания | 84.1 с |
| GUI `library_gui` с Calibre | 34.4 с |
| GUI `library_gui` со своим конвертером (WebP q35) | 30.5 с |
| GUI с AVIF, минификацией, шрифтами и Stored (16 потоков) | 52.8–60 с |
| GUI с правилом штриха и `avif_speed 4` (прошлый заход) | 109.7 с |
| **GUI, только AVIF, адаптивная скорость, лестница (текущие)** | **59.9 с** |

(102 с в позапрошлой строке — это тот же прогон на машине, загруженной
посторонней работой на 8 ядер; цифра снята на свободной.)

Последняя строка — плата за качество: `avif_speed` снижен с 8 до 4, а AVIF на
этом уровне ищет дольше. Если скорость важнее ~10 % размера картинок, верните
`avif_speed: 8` — импорт снова уложится примерно в минуту.

Книги обрабатываются параллельно — обычными `std::thread` по числу ядер,
картинки внутри книги кодируются последовательно. Раньше здесь был вложенный
`par_iter`, но с AVIF он несовместим: `ravif`/`rav1e` сами зовут rayon и
«воруют» работу из нашего же пула, из-за чего стек уходит во вложенность
глубиной в число картинок книги (подробнее в разделе «Бенчмарк»). На батче из
14 книг при 16 ядрах разницы не видно — книг больше, чем ядер, и каждый поток и
так занят своей книгой; проигрыш был бы заметен только когда книг меньше, чем
ядер. Число потоков задаётся в верхней панели (`0` = все ядра) и видно в нижней
панели во время импорта.

Основа времени — картинки: 582 штуки пережимаются в WebP и AVIF, и это ~95 %
работы (AVIF-кодирование примерно вдвое дороже WebP). Конвертация FB2 → EPUB
теперь почти бесплатна:

| 14 книг, один поток | Время |
|---|---|
| **`fb2epub::convert`** | **1.32 с** |
| `ebook-convert` (Calibre) | 19.95 с |

То есть свой конвертер быстрее Calibre в 15 раз, и на него приходится около 4 %
времени импорта вместо прежних ~16 %.

```bash
# сконвертировать один FB2 без окна и без импорта
./target/release/library_gui --convert book.fb2 /tmp/book.epub

# замерить каждый шаг оптимизации на своём архиве
./target/release/library_gui --bench /путь/к/архиву.zip /tmp/bench

# достать книгу и убедиться, что это валидный EPUB
arx dump data/archives/*.arx 821884.epub > /tmp/check.epub
unzip -tq /tmp/check.epub

# что внутри: все ли картинки в WebP/AVIF и совпадают ли media-type в OPF
arx extract -C /tmp/books data/archives/*.arx
python3 - <<'PY'
import zipfile, glob, re
for p in glob.glob('/tmp/books/*.epub'):
    z = zipfile.ZipFile(p)
    imgs = [n for n in z.namelist()
            if n.lower().endswith(('.jpg','.jpeg','.png','.gif','.bmp','.tif','.tiff','.webp','.avif'))]
    bad = [n for n in imgs if not n.lower().endswith(('.webp','.avif'))]
    opf = z.read('content.opf').decode()
    items = re.findall(r'<item [^>]*href="([^"]+)"[^>]*media-type="([^"]+)"', opf)
    wrong = [(h, m) for h, m in items
             if h.lower().endswith(('.webp','.avif'))
             and not (h.lower().endswith('.webp') and m == 'image/webp'
                      or h.lower().endswith('.avif') and m == 'image/avif')]
    print(p, 'картинок:', len(imgs), 'не-WebP/AVIF:', len(bad), 'кривой media-type:', len(wrong))
PY
```
